## 1. What was missing was a `ShapeSpec`

`P2.T22` left the row `aborted` for one reason: the 149-port vehicle had no
shape, so `equiv` had no `ScopeSpec` and could only run the whole-device
calibration. `fuzz/gw5ast138c/shapes/ae350_soc.py` is that shape, and it is
data-driven — buses, widths, directions and the 27 unmapped bits are read from
`extra_func[(0, 159)]['ae350']`, so a correction to the map changes the vehicle
with no edit to the shape.

| | |
|---|---|
| ports | 149, all 884 mapped bits connected, 27 unmapped left open |
| input bits | 410 on their own shift-chain flop, 6 on their own clock net |
| output bits | 464 on a 2-input XOR chain, 4 on a pinned flop |
| clocks | `CORE_CLK` ← `PLL_R[0].CLKOUT1`; `DDR/AHB/APB/RTC/DBG_TCK` ← five ripple stages |
| pinned | `u_pll` at `PLL_R[0]`, 8 named port flops at `R2C161[0..3][A|B]` — **both** flows |
| scope | row 0 columns 145-181, plus the three `PLL_R[0]` tiles |

The fold is a chain of 2-input XORs, not `^cap`: a wide XOR maps to
`MUX2_LUT5..8`, which the unpacker does not decode, and 72 of them were the
bulk of `P2.T22`'s `c1` mismatch. It is the same reasoning that keeps the
`clocking_clkdiv2` context free of ALUs.

## 2. Head order

The map carries **seven** `CLK`-class input taps, not six: `INTEG_TCK` is the
seventh, and that is why the vendor bitstream of `P2.T22` showed a clock count
the dossier does not.

| | taps |
|---|---|
| the vendor realises | `(0,162)/CLK0`, `(0,163)/CLK2`, `(0,164)/CLK2`, `(0,165)/CLK0`, `(0,174)/CLK0`, `(0,179)/CLK0` |
| the open flow realises | the same six, **plus** `(0,87)/CLK1` |

The vendor never uses `(0,87)/CLK1`, the tap the `.dat` record names for
`CORE_CLK`; it takes the dedicated zero-delay hop from the PLL. The chipdb now
models that hop — one fuseless pip per PLL site into a dedicated wire of the
anchor cell — and no longer offers the tap, so the open flow takes the same
single hop (`core-clock.md`, `fuse-set-138c.md`, and the re-run recorded in
`summary.md`). The seventh map entry is recorded under
`extra_func[(0,159)]['ae350']['core_clk']['fabric_tap']` and bound to nothing.

Two taps are resolved to a port by their net's own source, not by the ordinal
rule:

| port | tap | evidence |
|---|---|---|
| `CORE_CLK` | `(0,87)/CLK1` | source wire `R28C178_MPLLCLKOUT1` — the PLL output itself |
| `APB_CLK` | `(0,165)/CLK0` | driven by `ck[2]`'s flop at `X150Y1/DFF0` |

The other four are driven through a global buffer that decodes to no cell, so
their assignment stays ordinal — named as such, not asserted.

## 3. The configuration fuses: superseded by `fuse-set-138c.md`

**This section's conclusion was reached the wrong way and its central claim was
wrong.** It argued from an empty intersection between two designs' band sets,
which cannot separate "no fuse marks the block" from "a fuse whose column
follows the ports a design uses" — under the second reading an empty
intersection is the predicted outcome.

`fuse-set-138c.md` settles it, with 0 vendor runs. Tile types 224 and 228 are
ordinary CLS logic tiles whose `shortval` tables live in exactly the tile rows
the 77 bits are in; `P2.T24`'s filter never subtracted those tables. With every
modelled table subtracted, all five AE350 bitstreams and the AE350-free control
carry **0** unmodelled set bits in all 216 tiles. Separately, four bitstreams
of the same 149-port shape give 3 bits, none, 3 bits and none as the fold and
the PLL site vary — so the set is not a function of the port set either.

Consequences, as they now stand:

- `GW5AST_138C.get_AE350_SOC_fuses` returns `[]`, on that measurement.
- `AE350_SOC` is **not** in `NON_FUSE_BACKED_BELS`. The block's presence is
  carried by the pips of its port taps and decoded by
  `gowin_unpack.parse_ae350`; `c1` requires the cell and recovers it.
- There is no un-emitted interface band and no Phase-9 precondition from it.

## 4. A checker defect this row found

A port tied to a power rail was compared by the endpoint digest of the rail.
`gowin_unpack` gives a tied `CE`, `LSR` or `ADCEN` the union-find root `VCC`,
and every unrouted port of the die joins that component: **310 040** endpoints
in the vendor bitstream against **6 120** in the open one, for the same design.
Two ports tied to the same rail therefore compared unequal — 21 in-scope
`conns` differences that were naming, not configuration. `equiv.net_label`
now compares a rail by its name. Fixed, not masked: a difference in what a
port is tied *to* stays visible.

## 5. Scope, and what is deliberately outside it

| tiles | in scope | why |
|---|---|---|
| row 0, columns 145-181 | yes | the block's own band |
| the three `PLL_R[0]` tiles | yes | `PLL_R[0].CLKOUT1 → CORE_CLK` is part of what this row proves |
| the 216 `ae350_config` tiles | **no** | ordinary fabric the vendor fills with the design's own logic; including them turns 0 in-scope cell differences into 1 515 (measured) |
| the pinned-flop tile `(160, 1)` | **no** | context (`F6`), and it carries the two synthesisers' flop decomposition: GowinSynthesis realises a bare `DFF` as the `DFFR` mode with `LSR` tied to `VCC`, yosys and nextpnr as plain `DFF` — 16 attribute items over the 8 flops (`S6`, `D32`, §5.1d; §5.3 forbids masking it) |

## 6. The io-config residual, classified (`D34`/`D35`)

Out of this row's scope, and enumerated whole-device:

| class | bits | tiles |
|---|---|---|
| `io_used_pin_config` | 333 | 167 |
| `io_nondefault_config` | 309 | 154 |

These are `IOBA`/`IOBB` longval fuses of pins **at least one side
instantiates**, and values reachable by a `DRIVE` or `PULLMODE` attribute.
That is **not** the base mask's unused-IO default class — that entry covers
only pins used by neither design with both sides carrying a defaulted value —
so the answer to "is it already in the base mask?" is **no**, and it must not
be added: a used pin's IO configuration is the PR #423 class. It stays a named
gap owned by W-IO (Phase 3).
