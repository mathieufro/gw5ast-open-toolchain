# `AE350_SOC` port map of record — GW5AST-138C

**This file supersedes every earlier statement of the map.** Where
`wire-map-138c.md`, `portmap-138c.md` or `e0-138c.md` disagree with it, they are
retracted, and each carries a banner saying so. Their *measurements* stand; what
is retracted is the 867/44 pairing and `e0-138c.md` §5's direction convention.

Machine-readable companion: `portmap-reconciled-138c.json`, regenerated by
`tools/derive_ae350_portmap_reconciled.py` (`--check` fails if it has drifted).
It is generated from the chipdb nextpnr actually loads —
`apycula/GW5AST-138C.msgpack.xz`, sha256 `7f3c64c9…` — resolved through the
Himbaechel nodes, so it is the map as the router sees it and not a
re-derivation of it. **0 vendor runs**: both bitstreams are banked.

## 1. The direction convention, and why `e0-138c.md` §5 has it backwards

> A tap's direction is its **wire's role in the routing graph**, never the
> `.dat` table the record came out of.
> **`A`, `B`, `C`, `D`, `CE`, `CLK`, `LSR` are the block's INPUTS.**
> **`F`, `Q`, `OF` are the block's OUTPUTS.**

Die row 0 is a row of routing tiles with no bels (`ttyp` 242: 125 pips, zero
LUT/DFF sites), so a tap there is an ordinary local wire with exactly one
possible driver. `A`-`D`/`CE`/`CLK`/`LSR` are pip *destinations* — the fabric
drives them, and in a bel-less tile nothing reads them unless the hard block
does, so they are inputs. `F`/`Q`/`OF` are pip *sources* — the fabric reads
them, and nothing in a bel-less tile can drive them except the hard block, so
they are outputs.

`e0-138c.md` §5 states the opposite: inputs on `F`/`Q`/`OF`, outputs on
`A`-`D`/`CLK`/`CE`/`LSR`. That reading came from the table names
(`Ae350SocIns` → inputs), and in wire-class terms it cannot be right:

* an input on an `F`/`Q`/`OF` wire is a sink no pip can reach, because no pip
  in row 0 ends on one — which is exactly the router failure `e0-138c.md` §4
  recorded (`Failed to find a route for arc 1 of net drv[390]`);
* an output on an `A`-`D`/`CE`/`CLK`/`LSR` wire is a source no pip can read,
  because no pip in row 0 starts from one;
* under §5's polarity, `CE`, `CLK` and `LSR` taps would be *outputs* — but the
  block has no clock, enable or reset output at all, while it has exactly 13
  clock-enable, 6 clock and 2 reset inputs, which is the tap count on those
  three lines to the bit.

§5 is therefore retracted as a direction convention. Its per-tile and per-class
tallies are kept in place as the record of what was believed.

## 2. The cross-check: every bit against the run-1 pips

Source: the banked vendor bitstream `ae350-tilewires/run/impl/pnr/run.fs`
(sha256 `2f0c74d259ea8251b280cf11bd1c43eb95a34a384e94da44d7aeccec9ae54441`) and
its no-block control `ae350-baseline` (sha256 `525b45f2…`), decoded per die-row-0
tile with `apycula.gowin_unpack.parse_tile_` over `chipdb.tile_bitmap` — the
same unpacker the open flow uses. The decode is banked as
`apicula/tests/data/ae350-pip-roles-138c.json` (sha256 `ed50fadf…`, 29 KB) so no
test needs the 34 MB bitstream. The control decodes **five** row-0 tiles
(columns 0, 1, 7, 12, 181) and not one inside the block's band, so every band
pip in the other run is the block's.

The decision is made per bit, not per class: a mapped bit is an **input** if the
vendor ends a pip on its wire in its tile, an **output** if the vendor starts a
pip from it. It is not decided by routability, and it is not decided by the
regex it is being checked against.

| input | `B` | 101 (pip destination) | 0 |
| input | `C` | 96 (pip destination) | 0 |

| input | `CE` | 13 (pip destination) | 0 |
| input | `CLK` | 6 (pip destination) | 0 |

**No direction had to be flipped.** `_ae350_wire_drives_block` and the vendor's
routing agree on all 868 bits the vehicle exercises, and on none does the

The class rule is also confirmed as a rule, over every decoded row-0 tile and
not only the block's own taps:

| used as | `A` | `B` | `C` | `D` | `CE` | `CLK` | `LSR` | `F` | `Q` | `OF` |
|---|---|---|---|---|---|---|---|---|---|---|
| pip destination | 288 | 288 | 288 | 288 | 108 | 108 | 108 | 0 | 0 | 0 |
| pip source | 0 | 0 | 0 | 0 | 0 | 0 | 0 | 288 | 288 | 164 |

1476 destination uses against 0 source uses on one side, 740 source uses against
0 destination uses on the other. No row-0 wire is ever used both ways.

### What the pips do not decide — 16 bits, 15 of them provisional

The sixteenth is `CORE_CLK`, which the routing graph cannot decide because it is not a fabric tap at all; it is decided by the vendor timing report instead, and is not provisional.

| bits | why | status |
|---|---|---|
| 13 `OF` outputs in columns 156-157 (`DMA_ACK6`, `HRESETN`, and `ROM_HADDR` 0, 3, 6, 7, 12, 13, 18, 19, 20, 21, 23) | this vehicle sets no pip on those wires, so the run neither confirms nor contradicts the bit | **provisional**: direction rests on the class rule above, which the same run decides with 740 uses and no counterexample. `HRESETN` is additionally an `output` in the vendor post-PnR netlist `run.vo` (`.HRESETN(oraw[9])`), which is a second source for that one |
| `ROM_HADDR28` at `(0, 22)/F7` and `ROM_HADDR30` at `(0, 23)/OF3` | those tiles are absent from the vendor bitmap entirely — every bit zero — so the run says nothing at all about them | **provisional**: class rule only |
| `CORE_CLK` | not a fabric tap: the chipdb binds it to the dedicated PLL hop (`AE350_SOC_CORE_CLK`), so the routing graph does not decide it | **not provisional, decided elsewhere** — the vendor timing report `run.tr` gives `CLKOUT1` → `CORE_CLK` at `tNET 0.000 ns` (`core-clock.md`) |

Which source was used, plainly: the **pips** decided the 868, and they are the
only per-bit source available, because the `.tr` and `.vo` name ports, not tap
wires. `run.vo`'s `AE350_SOC` instance carries only the block's 149 scalar
ports and no bus bit, so it can confirm a *port's* direction and never a bit's
wire; it was used exactly that way, for `HRESETN` and for the six clock inputs.

## 3. The reconciliation arithmetic: 867/44 → 884/27

Both generations are in git and both are recomputed here, never quoted.

| generation | commit | inputs bound | outputs bound | total bound | unbound |
|---|---|---|---|---|---|
| previous | `153954b` (`P2.T08b`) | 398 / 416 | 469 / 495 | **867** | **44** |
| current | `6e58e8b` (`P2.T22`) onward | 416 / 416 | 468 / 495 | **884** | **27** |

`6e58e8b` is the flip. It did not find new records: it re-partitioned the same
two tables under the corrected direction convention. `Ae350SocOuts` slots 44-477
— 416 slots, every one live and every one on an `A`-`D`/`CE`/`CLK`/`LSR` wire —
are the whole input map; `Ae350SocOuts`'s head (slots 0-43) and tail (478-494)
plus `Ae350SocIns` between them are the output map.

Exactly which bits changed status, and why:

* **inputs +18**, bits 33, 67, 71, 76, 109, 113, 119, 123, 126, 160, 227, 260,
  264, 269, 273, 276, 376, 409. Those are the 18 sentinel slots of
  `Ae350SocIns`. The old reading put `Ae350SocIns` on the *inputs*, so each
  sentinel left an input bit unbound; the correct reading puts that table in the
  output map, so those 18 input bits now come from live `Ae350SocOuts` slots
  instead. No input bit was lost: 398 → 416, with 0 going the other way.
* **outputs −1**: 18 bits lost, 17 gained.
  * lost — output bits 77, 111, 115, 120, 153, 157, 163, 167, 170, 271, 304,
    308, 313, 317, 320, 420, 453 and 477: the same 18 sentinels, which the
    corrected reading moves *into* the output map, where they now leave output
    bits unbound (bit 477, `SCAN_OUT3`, is the one that falls past the end of
    `Ae350SocIns` inside the run — reason `no-record` rather than `unbound`);
  * gained — output bits 47, 57, 69, 86, 99, 134, 169, 237, 241, 248, 252, 255,
    321, 409, 442, 468 and 472: the 17 live `Ae350SocIns` slots that sit past
    input bit 415. The old reading discarded them as beyond the input range;
    under the corrected one they are ordinary output bits.
* **net**: 867 + 18 − 18 + 17 = **884**; 44 − 17 = **27**.
* **796 bits stayed bound and moved wire** (398 inputs + 398 outputs), because
  the two tables swapped roles. The pairing "867 bound *and* 27 unmapped" was
  never true of either generation: 867 goes with 44, 884 goes with 27.

exists in no wire table, so nextpnr can neither route it nor alias it to a real
wire: a design that drives one fails naming the port instead of being routed
somewhere plausible and wrong. The reason is the one `fse_create_ae350` recorded

unmapped.

This is a device-data residual, not a modelling gap: the sentinels are what the
vendor `.dat` ships. Whether the vendor splits this map across numbered tables
the way it splits `MDdrDllIns1`-`7` is open, and a per-bit trace would settle
it; no run was spent on it here.
