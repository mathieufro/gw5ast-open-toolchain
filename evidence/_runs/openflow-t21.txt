## Coordination note answered: the chipdb .bin and lzma.LZMAError
1. nextpnr DOES load the installed/explicit .bin. It always did: the T16b
   smoke was real and the T21 run resolves the device, places, routes globals
   and finishes normally.
2. The `lzma.LZMAError` T20b saw is not a defect: `chipdb-GW5AST-138C.bin` is a
   raw bbasm binary (`file` says `data`), NOT an xz stream. Only
   `apycula/<device>.msgpack.xz` is xz-compressed, and that is what
   `gowin_pack` reads (`gowin_pack.py:462`, via `importlib.resources`).
   Feeding the nextpnr .bin to a Python chipdb loader is a category error.
   Nothing to fix; the two artefacts are different formats with different
   consumers.

## Blocker found and fixed: PINCFG had no input wires
The first open-flow attempt failed at routing:
    ERROR: No wire found for port UNK0_VCC on destination cell PINCFG.
    ERROR: Routing design failed.        (nextpnr exit 125)
Root cause, verified end to end:
- `dat_parser.py` read `CibFabricNode` at a fixed delta `RSTable5ATOffset +
  0x27254`. That is the Gowin IDE 1.9.10.03 layout (the release upstream
  apicula pins). Both 1.9.11.03 and 1.9.12.03 `.dat` files hold the table
  0xb8 further on, at `+0x2730c` -- confirmed on the archived Education
  1.9.11.03 tree and the installed Standard 1.9.12.03 tree, and for GW5A-25A
  as well as GW5AST-138C.
- Reading the stale delta returns an all-0xffff grid, which is *silently
  legal* (0xffff is the "port absent" marker), so
  `chipdb.fse_create_pincfg` emitted `{'ins': {}}` while
  `chipdb.py:4172/4183` still set `HAS_PINCFG`.
- `nextpnr` then unconditionally packs a PINCFG cell with UNK0..3_VCC + SSPI
  (`himbaechel/uarch/gowin/pack.cc:56-71`) whose ports have no bel wires.
  Consequence: NO design of any shape could be routed on our chipdb.
- Stock `apycula==0.33`'s own parser reproduces the empty grid on the same
  1.9.11 file, so this is an IDE-version drift, not a fork regression. Its
  shipped GW5AST-138C chipdb has the right values only because it was built
  from 1.9.10.03 device files.

Fix (data-driven, version-tolerant): `dat_parser.Datfile.read_cib_fabric_node`
tries `CIB_FABRIC_NODE_DELTAS = (0x27254, 0x2730c)` and takes the first
*populated and plausible* grid, so a 1.9.10 file still reads at its own offset
and a future relocation is one list entry. Guards added:
`tests/test_dat_cib_fabric_node.py` (2 tests, both devices + the built chipdb).

Result after the fix, matching upstream apycula 0.33 exactly:
  extra_func[(108,166)]['pincfg']['ins'] =
    {'SSPI': 'D7', 'UNK0_VCC': 'B5', 'UNK1_VCC': 'D5',
     'UNK2_VCC': 'PINCFGUNK2_VCCC0', 'UNK3_VCC': 'D6'}
