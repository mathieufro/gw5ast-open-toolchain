## What changed (`apycula/chipdb.py`)

| Function | Was | Is |
|---|---|---|
| `gw5_hclk_idx` | `return -1` for every device but `GW5A-25A` | resolves `(row, col)` against `_gw5a_hclk_locs[device]`; the 25A region classifier is kept verbatim |

| `gw5_make_hclk_pips` | default-PIP and epsilon sections `for … in range(4)` (with an `XXX … for the 138C`) | `range(gw5_get_num_of_hclks(device))` |

Every fuse-bearing tile is a measured block cell and no other; all six carry
the same 151. **The 138C `.fse` HCLK fuse tables are not structurally
different from the 25A's** — table 48 is walked the same way and yields the
same per-block count on every block. Sample fuses (block 0, (27,0)):
`HCLK_UNK11 -> HCLK_TO_GCLK00 {(6,0)}`, `HCLK_UNK21 -> HCLK_TO_GCLK00
{(6,0),(6,8)}`, `HCLK_UNK6 -> HCLK_UNK10 {(8,3)}` — each fuse a `(row, col)`
bit coordinate, as the shape check asserts.

The block-1 node count was 166 before `gw5_make_pin_to_hclk` was keyed by
device: the 25A board entry put one spurious `HCLK1_*` node on an unrelated
138C cell. All six blocks are now identical at 165.

## Recorded, not fixed (each needs a measurement Phase 1 has no budget for)

1. **The inter-HCLK fuse branch of the table-48 walk is dead code**, on both
   devices: `elif srcid in range(hclk_off, hclk_off + 4*ihclk_wire_num) …`
   (`chipdb.py`) is nested inside `if srcid < hclk_off:`, so its condition can
   never hold. Consequence: no inter-HCLK pip carries a fuse anywhere, and the
   five 138C bridge cells contribute nothing — which is why leaving them at
   `hclk_idx == -1` loses nothing today. Repairing the indentation would move
   the GW5A-25A baseline, so it is an upstream conversation, not a drive-by.
2. **The `HCLK_IHCLK_*` crossbar defaults below it are 4-block literals.**
   Blocks 4 and 5 get their `HCLK_FROM_IHCLK4x/5x` and `HCLK_TO_IHCLK4x/5x`
   nodes but no crossbar entry. Which inter-HCLK output feeds which block on
   the 138C is not measured.
3. **`gw5_make_hclk_to_clk_gates` cannot fire on the 138C at all.** Measured:
   `clknames_5ast138c` defines **0 of the 16** `{T,B,R,L}BDHCLK{0..3}` names
   the function's grid scan looks for (the 25A defines all 16, and its four
   gate cells fall out of the `.fse` exactly as the in-tree literals say:
   ttyp 187 → (27,91) R, 257 → (10,0) L, 393 → (36,46) B, 410 → (0,59) T).
   So no HCLK→GCLK gate pip exists on this device. This is what blocks P1.T11
   from routing (`clkdiv-138c.md`) and is the next piece of the S10/S12 seam.
